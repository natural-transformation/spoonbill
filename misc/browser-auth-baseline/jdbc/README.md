# v3 JDBC host baseline

`JdbcReferenceHost.scala` and `JdbcBrowserSecurity.scala` are consumer-side integration against the existing 3.0 APIs. They are registered in `securityJdbc / Test` and the baseline application project, outside published framework artifacts. Both entire Scala files count toward the consumer production inventory: moving host SQL, custody or registry glue here does not remove it from the comparison. The host's `afterStage` callback is deterministic failure/barrier instrumentation and is disabled during timing measurements.

These fixtures do not establish that the complete Phase 0 browser application or performance matrix has passed. They contain no application JavaScript. The guarded adapter resolves cookie-bound connection authority, supplies projected root snapshots, and exposes the official completion configuration. The enclosing transport must issue the binding cookie and enforce exact origin before its HTTP logout wrapper. `CookieCredential.transportValue` is for trusted HTTP delivery, never presentation state or a result cache.

## Single-node guarded integration

`JdbcBrowserSecurity` requires explicit `singleNodeExclusiveWriters=true`. The supported deployment has exactly one adapter instance owning every application authority writer. A second process or out-of-band SQL mutation does not participate in its publication boundary and is unsupported. Its underlying host/browser adapters are private; application handlers use its gated methods. The standalone `JdbcReferenceHost.browser` remains a trusted regression port, not the guarded application's route into storage.

A bounded asynchronous gate serializes authority boundaries through actual outer transaction settlement. Waiting jobs acquire no JDBC connections and block no workers. Domain SQL runs on the supplied blocking executor. The durable clock also performs synchronous checkpoint SQL before observations, including v3's synchronous snapshot callback; this caller cost is part of the reference. No registry monitor is held across an effect or JDBC call, even with an inline execution context. Rejected dispatch settles waiters and shutdown. This global serialization is explicit baseline cost, not a performance recommendation or a candidate SPI.

Fresh joined SQL checks account/session, browser slot and view ownership in that order. Principals compare subject, session, realm, namespace, scope, security version, policy version and slot generation. Anonymous captures also retain their original generation and reject a missing credential when that slot has an active session. Handler proof completion and recovery invoke the captured connection check in their actual host transaction. The protected preference mutation uses the existing `OneUseOperationProtocol` and `JdbcOperationOutcomes`, including its earlier identity fences, on the same connection as current policy and the mutation.

Registry changes remain staged until acknowledged commit while the gate excludes all supported writers. Publication also checks that its original local claim survives and has not expired. Failure invalidates only the affected lease; an old-owner failure or close cannot erase its successor. Every takeover, release, logout and policy change detaches old snapshot leases before dispatch. A failed revocation therefore requires fresh presentation rather than restoring old state. Late acknowledged view acquisition releases its durable owner if local publication is no longer allowed. Unknown settlement fails closed; retained ownership/fence rows are never deleted to reset counters.

The guard's `ViewSnapshotSession` projects immutable non-sensitive root presentation onto freshly authorized state, selecting the v3 ResetView path. Component state is ephemeral. Same-identity reconnect can reuse the selected projection; changed identity or process restart starts fresh. Restart may claim an existing bound durable view with a higher epoch; unknown IDs allocate no durable row and use v3's missing-view terminal reload. Snapshot reads check local lease/expiry synchronously, which is sound only because every supported revoker shares the gate and detaches the lease before SQL. Sensitive disclosure remains default-deny. The adapter's node limit/count covers its own stored projection/bootstrap maps, not the separate cached component graph that v3 creates for a snapshot-enabled live session; complete graph bounds/accounting remain a reviewed measurement input.

The executable application uses the shared [`ReferencePolicy`](../common/README.md): 1,024 active views, at most sixteen per binding, 1,024 disconnected views, 1,024 bootstrap entries, 10,000 stored nodes per view, 32,768 retained rows per host history kind, 131,072 durable view epochs, 65,536 audit rows and 256 ordinary queued jobs. A full browser workflow can allocate up to eight view identities across activation, navigation and logout, so view history has a separate bound from host history. Bootstrap/reconnect TTLs are fifteen/thirty seconds. Password and factor work shares five attempts per browser and per `(browser, account)` tuple per sixty-second window. Each rate-window map is bounded at 32,768 entries. Direct regression constructors retain their earlier small defaults and are not the measurement profile.

`ReferenceAdmission` also bounds 256 callbacks before executor/gate submission, through actual settlement. `callbackCounts` and `Resources.pendingCallbacks/peakCallbacks` expose that ownership. Guard release has a separate priority queue bounded by the active-view limit, and aliases share one cleanup operation. One reserved maintenance slot coalesces pending/running retirement requests and runs after guard cleanup but before ordinary work. The queued-resource count includes all three SQL queues. Callback saturation does not consume cleanup or maintenance admission. Exhaustion fails closed; durable binding/view rows and replay fences are retained. Shutdown rejects ordinary queued work, drains admitted callbacks and SQL settlement, and then clears owned presentation and issuance resources. `retainedCounts` performs one explicit diagnostic query covering the stored authority tables; its cost is separate from domain work unless included by the measurement protocol.

The application ports are `bootstrapBinding`, `begin`, `password`, `factorForCeremony`, `recover`, `authority`, `actionAuthority`, `protectedAction`, `protectedPrincipal`, `logoutBinding`, and `completionConfig`. Factor resume derives the selected subject from the durable ceremony, so the UI need not send a subject field. The completion configuration receives only the official service's already origin-checked attempt/binding pair; it does not fabricate request headers. Schema initialization and account seeding remain explicit deployment operations, never request callbacks.

## Shared Scala reference application

[`JdbcReferenceApplication.scala`](../app/JdbcReferenceApplication.scala) maps the JDBC outcomes into the same [`ReferenceApplication`](../app/ReferenceApplication.scala) UI used by the memory provider. It projects only display message, ceremony/challenge lookup IDs, recovery flag and displayed counter. Account identity and protected routing are rebuilt from fresh authority. The shared profile seeds 1,000 synthetic accounts, preserving `alice / password` and `bob / password` with factor `123456`; the protected counter is per account. Both servers select `--proof=short` or `--proof=representative` PBKDF2-HMAC-SHA256 with 1 or 100,000 iterations, sixteen salt bytes and 256-bit output. `ReferencePolicy.json` reports actual constructor values.

[`JdbcReferenceServer.scala`](../app/JdbcReferenceServer.scala) uses the same official Pekko route as the memory server. It adds no JavaScript or transport implementation. It requires the disposable loopback `SPOONBILL_JDBC_TEST_URL` and uses `SPOONBILL_JDBC_TEST_USER`/`SPOONBILL_JDBC_TEST_PASSWORD` when supplied by the wrapper. `SPOONBILL_BASELINE_SCHEMA` selects an existing fixture schema; if omitted, a fresh schema name is generated and reported without connection details. All SQL identifiers are validated and quoted.

Start a new fixture explicitly:

```sh
env -u JAVA_HOME SBT_NATIVE_CLIENT=false \
  SPOONBILL_BASELINE_SCHEMA=baseline_reference SPOONBILL_BASELINE_INITIALIZE=true \
  nix develop --no-write-lock-file --command bash scripts/with-test-postgres.sh \
  sbt --batch --supershell=false -Dsbt.server.autostart=false \
  'browserAuthBaseline/runMain spoonbill.browserauthbaseline.JdbcReferenceServer 8080'
```

`--initialize` is the equivalent server argument. Initialization creates/seeds the selected schema once before binding the server. Restart against the same live database/schema with initialization disabled, including `SPOONBILL_BASELINE_INITIALIZE=false`. The process retains no old presentation: known durable views acquire a new owner and fresh projected root; unknown views reload. The server uses a public, explicitly synthetic AES key stable across fixture restarts and fresh `SecureRandom` nonces. That fixture key is not a deployment key-management design. The owning PostgreSQL wrapper removes its disposable database after the command exits. Coordinated shutdown drains the official binding, closes the guarded instance and shuts down its dedicated JDBC worker executor.

`bootstrapRecovery` retrieves only the latest eligible original ceremony/challenge metadata for the current binding and generation, ordered by expiry then ceremony ID. Policy and expiry are checked after locking its original record; `admitted` remains unresolved and must pass normal reconciliation. The shared page offers an explicit recovery button displaying the selected synthetic account while remaining unauthenticated. A valid committed pending cookie can render only the public bootstrap; the next physical WebSocket handshake remains the only activation boundary. The test-only `--pause-after-preparation` flag prints and flushes `SYNTHETIC_PREPARATION_COMMITTED:<attempt>` after acknowledged commit, then waits without a transaction or monitor held so the owning harness can kill/restart the process before a reply reaches the browser.

## Atomic domain and settlement

All host domain tables and the Spoonbill browser tables must share the same PostgreSQL database/schema and domain connection. `JdbcTransactionExecutor[Future]` owns one `Direct` transaction for preparation. Independent durable-clock checkpoints use a separate connection and committed transaction, which can overlap the domain connection. The serial guarded adapter requires a pool of at least two connections; a raw host allowing `N` simultaneous domain connections requires at least `N + 1` connections or an independently reserved clock pool. Otherwise every pool connection could be held by domain work waiting for its clock checkpoint. The executable fixture's data source opens independent connections without pooling. No SQL statement creates a Future. The callback is evaluated once; successful results are returned after acknowledged outer commit. Failed domain commit acknowledgment remains `CommitUnknown`; the same proof is never replayed.

An application with an existing outer runner supplies `existingRunner: Option[TransactionExecutor[Future, Direct, Connection]]`. This trusted infrastructure port replaces the supplied runner; it does not wrap a live connection in a second transaction. The runner joins the baseline program and any later host work, returns `Right` only after actual outermost commit, and preserves rollback/unknown disposition. Ordinary actions cannot assert commit with a Boolean. Runners exposing only savepoint completion or no reliable outer settlement are unsupported. The runner's connection must address the same configured atomic domain. Tests include a host outbox write after the baseline program, its rollback after a later host failure, and commit-acknowledgment loss after both writes.

The retained ceremony row fixes the completion-attempt ID at begin, before proof verification. Password computation runs outside the authoritative transaction. Account enablement and version are rechecked under the account lock after computation and again in completion. A challenged ceremony fixes subject, account version and challenge ID. Factor admission checks all three, and the admitted state prevents reissuing the same proof after rollback or restart.

The 3.0 integration needs an explicit durable admission transaction before completion dispatch, plus a process-local one-use claim. Both are part of this baseline's cost. Completion atomically consumes the ceremony, creates the host session, invokes `prepareNew`, inserts protected delivery material and writes the audit. A failure at any stage rolls back every staged change. This does not invoke the separate durable prepare-then-execute operation API.

Lock order is ceremony, account, host session, browser slot. Host hooks discover the immutable subject first, then lock account and session before the framework slot lock. Ceremony creation takes its capacity table lock before the slot; the global retained count therefore cannot race across bindings or introduce an inverted completion lock order. Recovery locks the same ceremony row as completion, waits for a live writer, and either reports its committed status or commits a negative fence excluding late dispatch. Negative fences and generation history are never deleted.

`recover` returns **status metadata only**, including when the historical commit has since expired or been revoked. It cannot mint an execution proof or delivery receipt. `deliver` independently runs the existing v3 current binding, host-policy, generation and expiry checks before ciphertext retrieval. Wrong binding, disabled account, expired completion and logout all prevent delivery or activation. A cookie response racing logout may be stale; activation rejects it.

## Credential custody and bounds

Injected entropy supplies 32-byte credentials, encoded as exactly 43 base64url characters. Authority tables contain only SHA-256 digests. JDK AES-GCM encrypts the recoverable 32-byte material with a fresh 96-bit nonce and authenticates realm, namespace, login purpose, attempt and browser binding as associated data. The infrastructure key remains outside SQL, and the same key must be supplied after restart. This fixture has a single configured key: a production rotation/key-ID protocol is not implemented here. Missing keys, malformed/tampered material or exhausted delivery return a typed failure and never fabricate another session.

Retrieval is limited to three attempts by an atomic SQL increment; failed decryption also consumes an attempt. Activation acknowledges the host session and deletes ciphertext in the activation transaction. Explicit `retireExpiredMaterial` deletes expired ciphertext without deleting the ceremony, audit or browser fences. Plaintext byte arrays are cleared after use; immutable transport strings cannot be erased on the JVM.

The executable profile separately bounds 1,024 live ceremonies, 1,024 retained delivery materials, and 32,768 retained ceremony/history rows. Consumed/expired ceremonies remain retained. Login and protected action audits share a 65,536-row retained table. Admission locks and freshly counts that table before host mutation; profile login also checks the material bound, and profile protected actions separately check the 32,768 outcome bound. Those extra SQL executions are explicit reference work. An audit insert failure rolls back the domain write and outcome together. This does not provide indefinitely reusable history: each measurement process/cell needs an isolated fixture schema. The profile's ceremony/challenge/delivery/session/operation-authority TTLs are 120/90/60/900/30 seconds. Direct tests without a shared profile retain the older 1,024-ceremony defaults and SHA-256 synthetic password verifier.

`JdbcReferenceClock` makes observed time nondecreasing across process restart. Before returning a newly advanced time it upserts the maximum into one `baseline_clock` row per realm/namespace and independently commits that transaction. Every new clock instance accesses storage before returning any time, even when the injected wall clock moved backward. The guarded adapter and its host share one helper; simultaneous independently cached writers remain outside the single-writer deployment contract. Seconds and nanoseconds are stored separately to preserve `Instant` exactly. Authentication rejection, domain rollback, and a crash after clock acknowledgment cannot roll back this clock row. Clock write or acknowledgment failure denies the current operation; the unacknowledged candidate is retained only for a local retry and is never used for authorization. After acknowledgment loss, reconstruction reads whatever maximum actually committed. Database durability and recovery must preserve acknowledged commits; destructive restoration of an older database snapshot is outside this contract.

Each clock advancement adds **one acquired connection, one UPSERT/RETURNING execution and one commit**, including checks that subsequently reject or roll back their domain transaction. Transaction settlement and the owner's disposal attempt precede the returned time; cleanup failure does not undo an acknowledged checkpoint. Equal/backward injected observations reuse only an already acknowledged process-local value. With the real nanosecond wall clock, multiple checks in one operation can each incur this cost; it is not a once-per-request amortization claim. Deterministic tests count both connections and the independent clock commit when expiry causes the domain transaction to roll back. Snapshot expiry also counts its synchronous checkpoint. The startup schema step explicitly creates the clock table; request paths contain no DDL.

Clock transactions use the existing `JdbcTransactions` owner. Storage failure and unknown settlement have stable clock error tags. Unknown commit or rollback is aborted before pool return; failed abort quarantines the connection without closing/resetting it, and the pool owner must recover or evict it. A close failure cannot erase an acknowledged checkpoint. Async authority lookup, proof capture, issuance and protected-operation admission dispatch their clock work onto the configured blocking executor. The ownerless synchronous storage-removal hint does no I/O; the owning guard releases SQL resources, while guarded reads and resource observations sweep expired local presentation. The synchronous snapshot callback remains an explicit v3 exception.

## Deterministic validation

From the repository root:

```sh
env -u JAVA_HOME SBT_NATIVE_CLIENT=false \
  nix develop --no-write-lock-file --command bash scripts/with-test-postgres.sh \
  sbt --batch --supershell=false -Dsbt.server.autostart=false \
  'securityJdbc/testOnly spoonbill.security.jdbc.JdbcReferenceHostSpec spoonbill.security.jdbc.JdbcBrowserSecuritySpec'
```

The suite requires the disposable loopback PostgreSQL wrapper and fails if its URL is absent. It covers password and challenged login, subject/challenge transplant rejection, replay, account changes during hashing and before completion, rate rejection, rollback at each atomic stage, commit acknowledgment loss and adapter restart, physical lock-wait recovery, negative fences, competing activation, logout, expiry, cryptographic material failure, delivery bounds, cleanup and retained capacity.

For the legacy direct-test constructor, with an unchanged deterministic clock already acknowledged by earlier proof work, standalone host preparation has **eleven frontend SQL executions, one acquired connection, one transaction commit and zero active connections afterward**. The executable profile additionally counts material capacity, and its protected action separately counts outcome capacity. Every newly advancing clock observation adds the checkpoint cost above. The guarded adapter additionally performs its coherent connection/view check. The existing-runner regression adds one host outbox statement on the same domain connection and commit. These are application JDBC executions, not wire round trips; disposable connection `SET search_path`/timeout setup occurs before probe wrapping and is excluded. Bootstrap, proof lookup/admission, delivery, activation and recovery are separate phases. These regression assertions do not freeze executable-profile or end-to-end login ceilings. Heap samples from `PerformanceProbe` do not establish peak or retained heap.

Native browser application evidence, multi-key rotation, full proof workloads and complete latency/memory evidence remain separate required gates. Existing one-use operation and WebSocket lifecycle suites remain regression requirements, not replaced by these fixture suites.
